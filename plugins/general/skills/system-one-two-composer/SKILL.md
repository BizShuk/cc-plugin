# System One / System Two 組合設計 (Composer)

把一個任務拆成原子步驟，判斷每一步該交給誰，再決定怎麼組合。

| 角色 | 負責什麼 | 比喻 |
|---|---|---|
| **CODE（程式）** | 流程控制、精確計算、查表、搜尋、執行動作、加權公式 | 食譜與計算機 |
| **S1 = System One（Jev）** | 固定選項內的快速判斷：Choice／Score／Noul，附機率與信心 | 檢傷護理師、藥師 |
| **S2 = System Two（一般 LLM）** | 生成文字與程式碼、多步推理、開放式問題、規劃 | 主治醫師 |
| **HUMAN（人工）** | 高風險且低信心、不可逆的決定 | 主任醫師會診 |

## 核心原則

1. **程式掌控流程 (code owns the workflow)**。模型只提供判斷或文字，順序、分支、組合都寫在程式裡。
2. **能用程式算的，就不要問模型**。數學、計數、日期比較、正規表示式能找到的東西，一律交給 CODE。
3. **型別只保證介面，不保證正確**。Jev 的「零幻覺」是格式永遠正確，不代表答案正確。
4. **每一階段都有信心門檻**。低信心的案件在發生的階段就攔下，不要往下傳（避免錯誤累積 error compounding）。
5. **S1 和 S2 是互補，不是取代**。S1 負責「決定」，S2 負責「寫」與「想」。

## 工作流程

### Step 1：釐清目標與限制

先確認（缺少的資訊可以合理假設，但要寫明假設）：

- **最終行為**：系統最後要顯示、選擇、修改、還是交接給誰？
- **呼叫量**：每天幾次？（量越大，S1 的價值越高）
- **延遲要求**：即時（< 1 秒）、互動（數秒）、批次（不在意）？
- **錯誤代價**：錯了能回復嗎？影響金錢、法律、安全嗎？

### Step 2：拆成原子步驟 (atomic steps)

從最終行為往回推，列出每一步的**輸入、輸出、依賴哪一步**。拆解原則：

- 一步只做一件事。「評估這份提案」要拆成市場、技術、差異化等獨立維度。
- 標出**依賴關係**：互相獨立的步驟可以在同一次 Jev 呼叫中並行；需要前一步結果的，必須分成兩次呼叫。
- 多步推理 (multi-hop)、多層間接 (indirection) 是 S2 的訊號，先嘗試拆開，拆不開才交給 S2。

### Step 3：用決策樹分類每一步

依序回答，**第一個成立的答案就是分類**：

```
Q1 能用確定規則、計算、查表、regex、搜尋完成嗎？
   → 是：CODE
Q2 輸出需要自由文字、程式碼、摘要或解釋嗎？
   → 是：S2（例外：若答案其實是從有限候選中挑選，改用 P7「先產生候選，S1 挑選」）
Q3 答案能列成固定選項（≤255 個）、有序等級、或是非題嗎？
   → 否：S2
Q4 一個懂行的人幾秒內能判斷嗎？（不需要多步推理、查其他資料、權衡多個因素）
   → 否：回到 Step 2 拆解；真的拆不開 → S2
Q5 判斷過程涉及數學、計數、日期先後、數值精度（例如 hex 色碼、RGB）嗎？
   → 是：把該部分切給 CODE，剩下的語意判斷才給 S1
Q6 需要的 state 能精簡到 32k token 內，而且大部分和問題相關嗎？
   → 否：先用 CODE 或 S1（Noul 相關性判斷）過濾
→ 以上都通過：S1（Jev）

最後再問一次：
Q7 這一步錯了會造成不可逆或高代價的後果嗎？
   → 是：在這一步後面加上 HUMAN 門檻（低信心時轉人工）
```

每一步都要寫出**分類理由**，特別是 S1 與 S2 的邊界判斷。

### Step 4：選擇組合模式

依照步驟之間的關係，從下表挑選一個或多個模式組合。每個模式的結構、適用時機、陷阱，詳見 `references/patterns.md`。

| 代號 | 模式 | 什麼時候用 |
|---|---|---|
| P1 | S1 單獨判斷 | 整個任務就是一個（或一組並行的）快速判斷 |
| P2 | 提早出口串接 (early-exit cascade)：S1 → S2 | 大部分案件簡單，少部分需要推理 |
| P3 | 投機式展開路由 (speculative fan-out routing) | 要分流到不同處理者，且各分支需要的參數可以先一起問 |
| P4 | 檢索 → S1 過濾排序 → S2 | RAG：S2 需要乾淨、精簡、無注入的資料 |
| P5 | S2 → S1 覆核 (verify) | S2 的輸出要進入自動化流程，需要檢查清單把關 |
| P6 | 三明治 (sandwich)：S1 → S2 → S1 | 同時需要入口分流與出口覆核的完整流程 |
| P7 | 先產生候選，S1 挑選 (select, not generate) | 答案是某個值或片段，但候選能用 CODE 或 S2 列舉 |
| P8 | 組合評分 (composite scoring) | 多維度評估，權重需要可調整 |
| P9 | 階層分類／束搜尋 (hierarchical / beam search) | 類別有很多層、總數超過 255 |
| P10 | 大量資料轉特徵 (map-reduce features) | 大量非結構化文字要轉成可統計、可訓練的欄位 |
| P11 | S2 設計、S1 執行 (S2 designs, S1 runs) | 題目與評分標準需要思考，但執行量很大 |
| P12 | S1 監督 S2 代理迴圈 (S1 guards agent loop) | S2 agent 每一步的動作都需要快速把關 |

選擇原則：

- **優先選最簡單能用的模式**。能 P1 就不要 P6。
- **呼叫量大 + 多數案件簡單 → 一定要考慮 P2**，這是最主要的省錢來源。
- **S2 的輸出會直接觸發動作 → 一定要加 P5**。

### Step 5：設計信心門檻 (confidence gates)

每一個 S1 步驟都要定義三段行為，門檻依錯誤代價調整：

| 信心範圍 | 行為 | 低風險動作的起始門檻 | 高風險動作的起始門檻 |
|---|---|---|---|
| 高 | 自動執行 | ≥ 0.7 | ≥ 0.9 |
| 中 | 確認、標記、或升級給 S2 | 0.5 – 0.7 | 0.6 – 0.9 |
| 低 | 轉人工或走後備路線 | < 0.5 | < 0.6 |

注意：

- 上表只是**起始值**，必須用真實資料校正。
- Choice／Score 才有 `confidence`；Noul 直接看機率，接近 0.5 代表「是」與「否」差不多可能，不是「中等程度」。
- 沒用到的分支，它的低信心可以忽略。
- 多個選項都可接受時，機率分散不一定代表有問題。

### Step 6：產出設計報告

使用下方〈輸出格式〉。如果使用者要的是實作，完成報告後再寫程式，API 細節以官方 typesafe-ai skill 或 https://docs.typesafe.ai/llms.txt 為準，不要憑記憶編造參數。

## Jev 限制速查（設計時的硬性條件）

| 限制 | 設計對策 |
|---|---|
| 不能生成文字 | 交給 S2，或用 P7 讓 S1 從候選中挑 |
| 不擅長數學、計數、日期比較、數值表示 | 交給 CODE；日期改成擷取年月日各一題 Choice |
| 字面理解 (literal reading) | instructions 寫出確切條件，邊界案例寫進 criteria |
| 多層間接推理表現差 | 拆題；在 state 中用欄位名稱直接指向相關資料 |
| 無關內容越多越不準 (context rot) | 先過濾；只送問題需要的欄位 |
| 可能被對抗內容影響 (prompt injection) | criteria 寫明確；上線前測試邊界與惡意案例 |
| 同一次呼叫的問題互相看不到答案 | 有依賴就分兩次呼叫；每個投機題的前提寫在題目裡 |
| Choice 選項上限 255 | 超過就用 P9 階層或兩階段（先各自評分再選） |
| 上下文上限：state + 全部問題 64k；state + 最長問題 32k | 大文件先切塊或檢索 |
| instructions 與 criteria 互相矛盾時會混亂 | 讓 criteria 成為 instructions 的延伸；避免「true 代表否」這類反向定義 |

以上數字以 jev-1.13 為準，新版本可能改變，實作前請查官方文件的 model jaggedness 頁面。

## 反模式 (anti-patterns)

- ❌ 問 S1「這整段推理正確嗎？」→ ✅ 拆成具體檢查：「結論有被第 3 段支持嗎？」
- ❌ 問 S1「清單裡有幾個 X？」→ ✅ 每項各問一題 Noul，CODE 加總
- ❌ 讓 S1「拆解任務」或「產生搜尋關鍵字」→ ✅ S1 勾選預先定義的子任務；CODE／S2 產生查詢
- ❌ 所有案件都送 S2 → ✅ S1 先分流，簡單案件提早出口
- ❌ 把 S2 的完整輸出原封不動交給 S1 判斷 → ✅ 只抽出要檢查的欄位或片段
- ❌ 一題問好幾個判斷 → ✅ 一題一個判斷，組合寫在 CODE
- ❌ 低信心的結果繼續往下傳 → ✅ 在該階段攔截
- ❌ 用 Score 的期望值換算精確數字 → ✅ 只用來判斷是否超過門檻

## 輸出格式

````markdown
# [任務名稱]：S1／S2 組合設計

## 1. 任務摘要
- 最終行為：
- 呼叫量／延遲要求／錯誤代價：
- 假設：

## 2. 步驟分類
| # | 步驟 | 類型 | 分類理由（決策樹停在哪一題） | 輸入 | 輸出 | 依賴 |
|---|---|---|---|---|---|---|
| 1 | | CODE / S1 / S2 / HUMAN | | | | — |

## 3. 組合模式
- 採用：P? + P?
- 選擇原因：
- 考慮過但不採用的模式與原因：

## 4. 流程圖
```
（ASCII 流程圖：標出每個步驟、類型、並行區塊、信心分支、提早出口）
```

## 5. S1 題目設計
每一次 Jev 呼叫列出：state 內容、並行的題目（id、類型、instructions、criteria）。
標明哪些是投機題、哪些題目有依賴需要下一次呼叫。

## 6. 信心門檻
| 步驟 | 高（自動） | 中（確認／升級） | 低（人工） | 理由 |
|---|---|---|---|---|

## 7. 預估效益
- S2 呼叫比例：原本 100% → 預估 ?%
- 延遲與成本的變化方向（以實測為準）

## 8. 風險
- 錯誤累積點、資料缺漏點、對抗輸入點，以及各自的對策

## 9. 驗證計畫
- 樣本數與人工標註方式
- 每個 S1 步驟：準確率、依信心區間分桶的準確率（校準檢查）
- 提早出口：S1 判斷「不需要 S2」的案件，與 S2 結果的一致率
- 上線順序：一次只加一個階段，量測後再加下一個
````
