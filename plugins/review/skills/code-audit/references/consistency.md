# 一致性軸 (Consistency Axis)

一致性問的是：`這份修改跟工作區其他地方矛盾嗎?`
單一檔案內部合理、但與另一處互斥的邏輯，是最貴也最難靠單檔閱讀發現的缺陷。

判斷基準永遠是`專案自己既有的作法`，不是外部風格書。

## 檢查鏡頭 (Lenses)

### 業務規則 (Business Rules)

同一個事件不得在兩處執行互斥的邏輯。

- 兩處對同一狀態轉移有不同的前置條件或副作用。
- 同一個限制（額度、期限、權限）在不同路徑有不同的數值或比較方向。
- 邊界條件不一致：一處 `>=` 一處 `>`，一處含頭不含尾另一處相反。

### 領域模型 (Domain Model)

同一實體在不同檔案的欄位與型別必須一致。

- 同名欄位型別不同（`string` vs `int64`），或零值語義不同（`0` vs `null`）。
- 同一實體在 A 檔有欄位、B 檔沒有，導致序列化後靜默遺失。
- 時間、金額、單位的表述漂移（秒 vs 毫秒、元 vs 分、`m` vs `cm`）。

### 數據合約 (Data Contract)

生產端 (producer) 的輸出必須符合消費端 (consumer) 的預期。

- API response、事件 payload、DB schema 與讀取端的欄位名或必填性不符。
- 錯誤格式不一致：一條路徑回錯誤碼，另一條回自由文字。
- 設定鍵值 (config key) 在宣告處與讀取處拼寫或預設值不同。

### 雙向參考 (Bidirectional References)

實體連結、caller/callee 合約必須雙向成立，單向引用即視為不一致。

- A 宣稱依賴 B，B 的介面卻沒有對應方法或已改簽名。
- 文件、註解或常數表列出的枚舉值與程式碼實際分支不對齊。
- 新增分支未同步更新對應的反向處理（新增狀態卻沒有對應的清理路徑）。

### 慣例一致性 (Convention Drift)

- 錯誤處理：同一層有的包裝 `%w` 有的直接回傳裸 error。
- 日誌：同一模組混用不同 logger 或不同結構化欄位名。
- 設定讀取：一處走既有 config loader，另一處直接讀環境變數。

## 執行步驟 (Procedure)

1. 從目標抽出它`觸及的概念`：實體名、狀態值、設定鍵、API 路徑、事件名。
2. 對每個概念在 repo 全域 `grep`，找出所有生產端與消費端。
3. 逐一比對上述鏡頭，記錄 `A 說 X -> B 說 Y`，兩側都附 `file:line`。
4. 只回報`可證實的矛盾`；風格偏好不屬本軸。

## 邊界 (Boundary)

目錄佈局、模組邊界、依賴衛生屬 `[[planner]]` 的系統軸；
文件與程式碼不符屬 `[[project-docs]]`；識別字本身的品質屬 [naming.md](naming.md)。
