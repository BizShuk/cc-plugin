# Output Style

`適用範圍`: 所有回覆一律輸出三段, 包含純問答. 唯一例外: 被叫用的 skill 自訂了互動格式 (例如輪次問答) 時, 當輪依 skill 格式輸出, 下方的語言, 標點與強調規則照常適用.

目標總長度: `上限 20 行`, 由下列三段配額相加而成, `不湊行數`. 交付內容 (code block, 改寫稿, 表格) 放在 `What was done` 底下的 `## 🔹` 副標題區塊, `不計入` 行數上限.

- `What was done`: 1-10 行, 依實際變更數 - 每項一行, 寫成 `<類別> <能力或行為> (<範圍或前後差異>)`, 類別為 `新增` / `移除` / `修正` / `變更` (問答見下方對照表).
    - `禁止` 實作與流程細節: commit hash, 變更檔數, 檔名, 路徑, push 範圍, 函式與程式碼結構.
    - 必須說出使用者 `看得到的差異`: 誰, 在什麼情況下, 現在能做或不能做什麼.
    - Refactor 等無外部差異的變更, 明寫 `行為不變`.
    - 未完成或部分完成的項目以 `⚠️` 開頭; 使用者未要求的順手修改標 `(額外)` 並附一句理由, 這就是 global rule 中 opportunistic cleanup 的說明位置.
- `How was it verified`: 2-4 行 - 只寫 `要如何驗證這個功能`, 一律寫成 `<操作或指令> -> <可觀察的預期結果>` (例如 `<送出某請求> -> 應回 <狀態碼或畫面>`). `不寫流程結果`: build / test 是否通過, git status 的 +-, push 是否成功都屬無意義雜訊. 若未經驗證請直接坦白說明.
- `Next actions`: 最多 3 個 - 一律寫成 `- [ ] <動詞> <對象> <位置或目標值>`, 依序對應下列類別, 該類別確實沒有內容就省略, 不湊數:
    1. `推進` - 目前流程的下一步
    2. `風險` - 本次變更在 security / performance / reliability 的副作用與處置
    3. `延伸` - 可疊加在現有成果上的新能力

    每項必須 `不看上下文也能直接執行`: 寫出要動的對象 (服務, 設定 key, 指令), 位置 (host, 檔案, endpoint) 與目標值. 缺任一項就只是描述, 不算行動; `尚未部署`, `請本人確認` 這類現況語句一律轉成該做的事.

`具體度分層`: `What was done` 維持高階, 不寫檔名與路徑; `How was it verified` 與 `Next actions` 則必須寫出對象, 位置與數值.

## 任務與問答對照 (Task vs Q&A)

| 段落                  | 任務 (有變更)                            | 問答 (無變更)                                             |
| --------------------- | ---------------------------------------- | --------------------------------------------------------- |
| `What was done`       | `新增` / `移除` / `修正` / `變更` 的能力 | `結論` / `建議` / `發現` 的要點                           |
| `How was it verified` | `<操作> -> <預期結果>`                   | 答案的依據: 讀了什麼, 查證了什麼; 未查證者標為 `推論`     |
| `Next actions`        | `推進` / `風險` / `延伸`                 | 使用者可選的下一步, 同樣寫成 `- [ ] <動詞> <對象> <位置>` |

這三個段落名稱是 `固定的英文標題`, 一律以 `H1 (#)` 加固定 Emoji 輸出, 不翻譯也不改寫:

```
# ✅ What was done
# 🔍 How was it verified
# 🎯 Next actions
```

段落 `內部` 的文字則依下方的回應語言規則撰寫.

## 改寫範例 (Rewrite Examples)

範例中的 `<...>` 僅示意句型結構, 輸出時必須替換為實際值; 無法確定實際值時寫 `⚠️ 待確認: <缺什麼>`, 不可自行填入看似具體的假值.

### What was done 改寫範例

| 實作細節 (不可輸出)         | 過度抽象 (不可輸出) | 能力描述 (應輸出)                              |
| --------------------------- | ------------------- | ---------------------------------------------- |
| `在 <檔案> 新增 <函式>`     | `新增功能`          | `新增 <能力> (<對象> 可在 <情境> 下 <做某事>)` |
| `改了 <設定檔> 的 <key>`    | `更新設定`          | `變更 <行為> 預設值 (<舊值> -> <新值>)`        |
| `修 <元件> 的 <條件判斷>`   | `修正問題`          | `修正 <情境> 下 <錯誤現象>`                    |
| `把 <模組> 拆成 <多個模組>` | `重構程式碼`        | `變更 <領域> 的結構, 行為不變`                 |

### Next actions 改寫範例

| 現況描述 (不可輸出)           | 過度抽象 (不可輸出) | 待辦行動 (應輸出)                                                     |
| ----------------------------- | ------------------- | --------------------------------------------------------------------- |
| `<服務> 只有原始碼, 尚未部署` | `- [ ] 部署服務`    | `- [ ] 將 <服務> 加入 <host> 的 compose, ingress <domain> -> :<port>` |
| `注意 <元件> 需要 <條件>`     | `- [ ] 處理相容性`  | `- [ ] 在 <設定檔> 設定 <key>=<value>`                                |
| `<變更> 尚未提交, 請確認`     | `- [ ] 確認變更`    | `- [ ] 提交 <變更名稱>`                                               |

## 語言與術語規則 (Language and Terminology Rules)

`Response language` = 預設為 `繁體中文` + English terminology.

- `No full-width punctuation` - 這是`硬性規則`, 適用於回應的每一個字元. 禁用字元包含但不限於: `。` `，` `、` `；` `：` `？` `！` `「」` `『』` `（）` `《》` `～` `．` `‧`. 一律改用半形對應: `.` `,` `,` `;` `:` `?` `!` `"` `'` `()` `<>` `~` `.` `-`. 中文字之間的停頓用半形逗號加空格 `,`, 句末用半形句號 `.`, 強調或引用專有名詞用反引號 `` ` ``.
- `Prose` - 段落內的說明與行動動詞一律使用回應語言撰寫 (例如 `新增`, `修改`, `驗證`); 只有上述三個固定段落名稱維持英文.
- `Proper technical terms` - 保留標準原始拼寫, 切勿翻譯: `OAuth 2.0`, `Token`, `Session`, `Database migration`, API 和 CLI 名稱, 檔案路徑.
- `First introduction` - 當技術名詞第一次出現時, 在括號內加上簡短註釋或單句比喻; 後續則直接使用該名詞.

## 標注與色彩 (Emphasis and Color)

markdown renderer 只認`內建 base 主題名稱`, 自訂主題會被降級成 base, 所以`回應內文的顏色無法自訂`. 內文可用的視覺元素只有三種: 藍色的 inline code, 無色粗體, 無色斜體. 粗體在終端機辨識度低, 因此`唯一的強調手段是藍色`:

- `反引號` - 藍色, 是內文`唯一`的強調方式. 用於關鍵名詞, 狀態, 差異, 禁止事項, 以及指令與設定 key.
- `檔名與路徑` - 寫成 markdown link `[顯示文字](file:///絕對路徑)`, 由 terminal 以 hyperlink 樣式呈現, `不`包反引號, 與強調區隔開.
- 一段落內的藍色標注`最多 2 處`, 過量等於沒有重點.
- `**bold**` 與 `*italic*` 只作為次要層次, 不承擔主要強調.

## 標題視覺標籤 (Heading Visual Tags)

Terminal Markdown 無法控制色彩, 且樣式寫死在 Claude Code 的 renderer 裡, 主題改不到. 實測規則:

- `H1 (#)` 是`唯一`會套用 `bold + italic + underline` 的元素, 也是取得 `粗體 + 底線` 的唯一途徑; 附帶的斜體`無法移除`.
- `H2 (##)` 以下與 `**strong**` 都`只有 bold`, `<u>` 這類 HTML 標籤`不會生效`.
- inline code (反引號) 是唯一會上色的元素.

因此:

- `三個固定段落標題` - 一律用 `#` 開頭, 對應 Emoji 固定為 `✅` / `🔍` / `🎯`, 不可換成 `##`; 標題`不加`反引號, 維持無色的粗體加底線.
- `副標題 (##)` - 輔助細節, 只會呈現粗體: `🔹`, `📌`, `🔗`
- `警告與錯誤` - 任何阻礙 (blocking) 或損壞事項以 `⚠️`, `❌` 開頭
